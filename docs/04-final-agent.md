# Этап 4. Собранный агент и его обвязка

## Цель и пользователь

Пользователь - разработчик продукта на языковой модели: чат-бота, ассистента
или агента. Его модель не знает событий после даты среза знаний и отвечает о
них неверно или никак.

Продукт - слой свежих знаний, подключаемый к агенту как MCP-сервер. В текущем
проекте его эталонный клиент сначала ищет в локальном корпусе, затем в живых
источниках, а при отсутствии подтверждения возвращает `FINAL: NOT_FOUND`.

Этапы 1-3 были экспериментами выбора: нужны ли инструменты, что даёт база по
сравнению с поиском, оправданы ли LangGraph и дополнительные надстройки.
Финальный слой оставляет только решения, оправданные ценой верного ответа.
Разработчик получает Docker-сервер и измерение на golden set: качество, цену,
задержку и разбор ошибок.

У текущего golden set 67 задач: 27 вопросов имеют ответ в базе, 30 требуют
живого поиска, ещё 10 проверяют поведение при отсутствии ответа в локальном
корпусе: пять задач требуют найти ответ живым поиском, пять - честно отказаться.

## Схема

```text
CLI или ноутбук
      │ синхронный вызов agent.run
      ▼
ReAct-агент ──► OpenRouter по HTTPS
      │
      └── Toolbox: allowlist + хуки + ограничение результата
                    │
                    ▼
          MCP-клиент в отдельном потоке
          с собственным asyncio event loop
                    │ Streamable HTTP
                    ▼
          mcp / mcp-eval в Docker
                    │
                    ├── Milvus: локальный корпус
                    └── Wikipedia, GEN, ESPN: чтение внешних страниц
```

Клиентский процесс не импортирует реализацию MCP-инструментов. Он видит
только MCP-схемы, получает их по HTTP и вызывает сервер через протокол.
`mcp` использует полный корпус, а `mcp-eval` - корпус без страниц, которые
должны находиться живым поиском. Это позволяет сравнивать конфигурации через
одинаковую удалённую границу.

## Как проходит один вопрос

1. `events-agent ask` подключается к `MCP_URL` и получает список инструментов.
2. `Toolbox` оставляет модели только разрешённые инструменты роли и сверяет
   их описания с `mcp_pins.json`.
3. `agent.run` отправляет модели системное сообщение и вопрос.
4. Если модель вернула `tool_calls`, `Toolbox` проверяет аргументы кодом,
   отправляет вызов MCP-серверу и ограничивает текст результата.
5. Результат возвращается в историю, после чего модель получает следующий ход.
6. Повтор вызова или восьмой ход переводит агент в режим ответа без
   инструментов. Это ограничивает зацикливание.
7. `final_answer` достаёт последнюю строку `FINAL:` для проверки и вывода.
8. Клиент закрывает MCP-сессию. Файл журнала содержит модель, токены, цену,
   инструменты, аргументы и задержки.

`MCP` выглядит синхронным для агента, но внутри держит один asyncio-цикл в
отдельном потоке. Методы `list_tools` и `call_tool` передаются в этот цикл
через `asyncio.run_coroutine_threadsafe`. Поэтому блокирующее ожидание CLI не
мешает сетевому циклу MCP обслуживать текущую сессию.

## Обвязка

### Хуки

`events_agent/hooks.py` содержит проверки границы между решением модели и
внешней системой:

- `before_tool` отклоняет пустой или слишком длинный запрос, проверяет число
  ключевых слов и допустимый сайт для `page_find`;
- `after_tool` удаляет нулевые байты и обрезает результат до лимита контекста.

Это именно проверки Python-кода: модель не может заменить их другой фразой в
системном сообщении. Ошибка становится сообщением инструмента для модели и
попадает в журнал.

### Контекст

`events_agent/context.py` считает размер истории в символах. Когда история
выходит за лимит, начало запроса и два последних полных раунда сохраняются, а
старые результаты инструментов заменяются коротким конспектом. Событие
`context` в журнале содержит размер до и после сжатия.

### Кэш промпта

Для моделей Claude `llm.cache_marks` преобразует стабильное начало и конец
кэшируемого префикса в формат `cache_control: ephemeral`, который понимает
OpenRouter. В журнале сохраняются `prompt`, `cached` и `completion`, поэтому
долю входа из кэша можно считать как `cached / prompt`. Для моделей с другой
схемой кэширования отправляется обычная структура сообщений.

### Деньги

`Journal.check_budget` вызывается перед каждым сетевым запросом к модели или
endpoint embeddings. Переменные `MAX_TASK_CENTS` и `MAX_DAILY_CENTS` задают
потолок задачи и дня. Провайдер сообщает фактическую цену только после
ответа, поэтому достигнутый лимит блокирует следующий вызов. `spent_today`
суммирует журналы текущей даты, а CLI печатает дневной расход.

### Налог инструментов

Размер JSON-схем инструментов оценивается как `len(json) / 4` токенов и
пишется в поле `tool_tax_tokens` каждого вызова модели. Вариант с базой имеет
дополнительную схему `knowledge_base`; вариант без базы позволяет измерить
цену этого контекста отдельно.

## MCP и безопасность

- `Toolbox` выдаёт модели allowlist: роль `агент` видит базу и пять поисковых
  инструментов, роль `агент без базы` - только живой поиск.
- `check_pins` сравнивает описание и JSON-схему инструментов с отпечатками в
  `mcp_pins.json`; неожиданное изменение останавливает запуск.
- Ключ OpenRouter хранится только в `.env` и передаётся контейнеру для
  embedding-запросов. В историю сообщений и git он не попадает.
- Внешние инструменты только читают данные. В проекте нет операции записи в
  сторонний сервис, запуска кода из ответа модели или необратимого действия,
  поэтому отдельное подтверждение записи не требуется.
- Текст из Википедии и других страниц считается недоверенным содержимым:
  он ограничивается по размеру, передаётся как результат инструмента и не
  получает полномочий менять allowlist или выполнять команды.

## Измерение

Набор и эталоны находятся в `data/`, а `events_agent/evaluate.py` строит одну
таблицу для трёх строк:

| Вариант | Что измеряет |
|---|---|
| сильная модель без инструментов | ориентир из сохранённых результатов прошлых этапов |
| база и поиск | основной агент с `knowledge_base` и живым поиском |
| только поиск | альтернатива без локальной базы |

Таблица печатает долю верных ответов, группы задач, вызовы, токены, долю
кэша, налог инструментов, цену, цену верного ответа и задержку. Полный прогон
67 задач завершён для обеих конфигураций mini:

| Вариант | Верно | В базе | Только поиск | Отказ | Вызовов на задачу | Токенов на задачу | Доля кэша | Налог инструментов | Центов на задачу | Центов за верный | Задержка, с |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| Sonnet без инструментов, старые трейсы | 8/67 | 1/27 | 2/30 | 5/10 | 1.0 | - | - | - | 0.2167 | 1.8150 | - |
| mini: база и поиск | 46/67 | 25/27 | 13/30 | 8/10 | 4.5 | 6060 | 0.360 | 3531 | 0.0808 | 0.1177 | 23.0 |
| mini: только поиск | 38/67 | 15/27 | 15/30 | 8/10 | 5.2 | 8211 | 0.404 | 3363 | 0.1060 | 0.1869 | 27.6 |

Основной вариант дал на 20 % больше верных ответов, чем только поиск, и был
примерно на 24 % дешевле за задачу. На вопросах с ответом в базе преимущество
составило 25/27 против 15/27. Только на отложенных страницах живой поиск
оказался немного лучше: 15/30 против 13/30. Это показывает, зачем нужны обе
части слоя: база закрывает известный корпус, а поиск помогает за его пределами.

Фактическая стоимость всех 134 трейсов составила 12.52 цента. Уже
имеющийся трейс повторно не вызывает модель. Для бесплатной проверки
сохранённых результатов:

```bash
uv run events-agent eval
```

Для отладки недостающих записей можно выбрать три задачи:

```bash
uv run events-agent eval --config "s4-1-база и поиск" --ids fresh-0 fresh-125 none-0
```

Запуск с `--yes` создаёт новые обращения к модели и выполняется только после
отдельного согласования расходов.

## Запуск

```bash
cp .env.example .env
# вписать OPENROUTER_API_KEY в .env
docker compose up -d --build
docker compose ps
MCP_URL=http://127.0.0.1:8090/mcp uv run events-agent ask "Who won the 2026 Indianapolis 500?"
```

Проверки без обращения к провайдеру:

```bash
uv run pytest -q
uv run events-agent eval
```
